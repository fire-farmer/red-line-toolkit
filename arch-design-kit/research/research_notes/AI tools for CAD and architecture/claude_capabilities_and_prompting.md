# Claude for 3D CAD and Architectural Drawings: Capabilities, Limitations, and Prompting/Workflow Method (as of Nov 2026)

*Evidence labels used below: **[Benchmark]** = published benchmark or paper result; **[Docs]** = official Anthropic/vendor documentation; **[Vendor claim]** = self-reported by a company or tool author; **[Anecdote]** = practitioner report or blog test. **[Older]** marks pre-2025 work or results on models that are now 2+ generations old. Some figures reached me only through search-result summaries, because arxiv.org and xda-developers.com could not be fetched from this session; those are marked "(via search summary)" and should be checked against the primary PDF before they are quoted.*

## 1. Capabilities: how well do Claude and other frontier LLMs read drawings and generate CAD/plan geometry?

### Takeaway
By late 2026, frontier Claude models are strong at **code-CAD generation** when they work as agents with a CAD kernel. Claude Opus 5.5 scores 100% on a small CadQuery benchmark and has the top point estimate on the agentic Parametric CAD Bench v3. They remain **weak at reading raw drawings and images, and at precise spatial reasoning**. General VLMs reach only about 33–38% accuracy on floor-plan CAD drawing understanding. Structured text or JSON input beats images, and code tools help with metric questions but not with spatial planning. Generation is good; perception and spatial judgment are the bottleneck.

### Cited Findings

**Reading drawings / floor plans (vision)**
- [Docs] Anthropic's vision docs: "Claude's spatial reasoning abilities are limited. It may struggle with tasks requiring precise localization or layouts, like reading an analog clock face or describing exact positions of chess pieces." They also say: "Do not use Claude for tasks requiring perfect precision or sensitive image analysis without human oversight" — [Anthropic vision docs](https://docs.anthropic.com/en/docs/vision)
- [Docs] Image resolution limits: an image whose long edge exceeds 1568 px, or that costs more than about 1,600 tokens, is scaled down (aspect ratio preserved) on the standard tier. Cost is about ⌈w/28⌉ × ⌈h/28⌉ visual tokens (28×28 patches). A 1920×1080 screenshot resizes to 1456×819, not 1568×882. High-resolution-tier models have a larger budget (4,784 tokens, per a localized docs page; via search summary) — [Claude vision docs](https://platform.claude.com/docs/build-with-claude/vision); [Vision coordinates docs](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)
- [Benchmark] **ArchPlanVQA** (J. Computing in Civil Engineering, 2026): general-purpose VLMs reach **only about 33–38% semantic understanding accuracy on architectural floor-plan CAD drawings**. The authors attribute this to CAD-converted images differing from everyday images in color, texture and semantic representation. The question types include OCR-grounded QA, counting, symbol recognition and spatial relations. The model list was not visible (via search summary) — [ArchPlanVQA DOI](https://dx.doi.org/10.1061/JCCEE5.CPENG-7571); [scite summary](https://scite.ai/reports/archplanvqa-benchmark-and-comprehensive-evaluation-r60AmAY3)
- [Benchmark] **AEC-Bench** (Nomic, Mar 2026; 196 tasks on real construction drawing sets, covering intra-sheet, intra-drawing and intra-project work such as detail title accuracy, note callouts, cross-reference resolution and tracing, sheet index consistency, spec–drawing sync and submittal review). It evaluated **Claude Code with Opus 4.6 and Sonnet 4.6**, plus Codex with GPT-5.x. General coding agents "partially generalize" but **fail on visual grounding, exhaustive traversal, and cross-document coordination.** Adding Nomic's structured drawing tools (extracted text, layout elements, reference relationships) produced large gains on retrieval-heavy tasks. On spatial-grounding tasks (note-callout accuracy, cross-reference tracing), "document parsing alone is not sufficient," and parsing could slightly reduce performance. I could not map exact per-Claude numbers from the bar chart. Nomic has a commercial stake in this benchmark — [AEC-Bench GitHub](https://github.com/nomic-ai/aec-bench); [Nomic announcement](https://www.nomic.ai/news/aec-bench-a-multimodal-benchmark-for-agentic-systems-in-architecture-engineering-and-construction); [arXiv 2603.29199](https://arxiv.org/html/2603.29199); [Nomic blog](https://www.nomic.ai/blog/what-does-aec-bench-mean-for-aec-firms)
- [Benchmark] **AECV-Bench** targets VLMs on drawings: object counting on 120 floor plans plus 192 drawing-grounded QA pairs. I did not retrieve its results — [ResearchGate AECV-Bench](https://www.researchgate.net/publication/399595749_AECV-Bench_Benchmarking_Multimodal_Models_on_Architectural_and_Engineering_Drawings_Understanding)
- [Benchmark] **AECBench** (knowledge, not vision): 4,800 expert-validated questions across 23 AEC tasks and nine LLMs. It found significant deficits "in interpreting knowledge from tables in building codes, executing complex reasoning and calculation, and generating domain-specific documents" — [AECBench HF](https://huggingface.co/datasets/jackluoluo/AECBench); [AECBench project page](https://archiai-lab.github.io/AECBench.github.io/)
- [Benchmark] aecbench.com (500+ tasks on topics such as seismic design and HVAC) showed Grok 4.3 at 0.89 and GPT-5.2 at 0.83 in the visible snapshot. Claude did not appear in the visible portion, and the page's date is unclear — [aecbench.com](https://www.aecbench.com/)

**Spatial reasoning over layouts (text/structured)**
- [Benchmark] **FloorplanQA** (ICML 2026): 2,000 symbolic layouts, 16,000 QA pairs, 8 task families (pair distance, free space, max box, view angle, obstruction, placement, repositioning, shortest path) and 15 LLMs. Models "succeed on shallow queries, but often fail to respect physical constraints and preserve spatial coherence." They struggle with navigation, overlap handling and following geometric constraints, though they stay mostly robust to small perturbations. Ground truth is computed with shapely, independently of any LLM — [arXiv 2507.07644](https://arxiv.org/html/2507.07644v2); [ICML poster](https://icml.cc/virtual/2026/poster/62946); [project page](https://olddelorean.github.io/FloorplanQA/)
- [Benchmark] In FloorplanQA, **the JSON-only condition is "the strongest condition in the paper."** Adding rendered images (schematic boxes, icons, or photorealistic conversions) did not beat structured JSON — [FloorplanQA GitHub](https://github.com/OldDeLorean/FloorplanQA)
- [Benchmark] In the FloorplanQA tool ablation, **a Python code interpreter raised placement accuracy from 64.5% to 95.0%**, and the paper reports +30–40 points on distance and angle tasks. The same tool **lowered shortest-path accuracy from 25.0% to 12.5%** because boundary contact was misjudged as collision. Planning and optimization tasks (free space, max box, shortest path) average only 5–45%. Which model these ablation numbers belong to was not clear, and v3 and v4 tables differ (via search summary) — [arXiv 2507.07644](https://arxiv.org/html/2507.07644)
- [Benchmark][Older/2025] A visual perspective-taking study found that VLMs, including Claude Sonnet variants, "excel in scene understanding" but decline significantly on spatial reasoning — [arXiv 2505.03821](https://arxiv.org/html/2505.03821v1)
- [Unverified claim] A news alert says Claude Opus 4.8 ranked last on "EyeBench-V3," a test that strips language scaffolding from visual tasks. I could not verify this against the benchmark — [aiweekly alert](https://aiweekly.co/alerts/claude-opus-48-ranks-last-on-eyebench-vision-test)

### Inferences
- **There is a sharp asymmetry.** Claude is near the frontier for *writing* CAD code (CadQueryEval 100% for Opus 5.5; best point estimate on Parametric CAD Bench v3), but every independent drawing-understanding benchmark (ArchPlanVQA, AEC-Bench, BenchCAD's image tasks) shows weak raw *perception* of drawings. A guide should tell users to give Claude numbers and structure, not pictures, wherever possible.
- **Model choice matters a lot.** On CadQueryEval, scores range from 40% to 100% across 2025–2026 Claude models, and the ranking is not monotonic (Sonnet 4.6 < Sonnet 4.5; Opus 4.7 < Opus 4.6). With only 25 tasks, the 95% CI at a 50% pass rate is about ±20 points (binomial SE ≈ 0.1), so gaps under about 20 points on that benchmark are noise. Recommend the newest Opus-class model for CAD code, and treat small benchmark gaps as noise.
- **Engineering drawings with dimensions behave differently from renders.** Parametric CAD Bench v3's image-to-CAD workflow, reconstructing from *dimensioned engineering drawings*, was Opus 5.5's best workflow (84.66%). BenchCAD found that *undimensioned target renders* drove models to near zero. Images help when they carry explicit dimensions and annotations that Claude can read as text. Images hurt when Claude must infer sizes from pixels. This is a cross-benchmark inference, not a controlled comparison.
- **Resolution arithmetic for full sheets.** A 36-inch-wide ARCH D sheet downscaled to 1568 px is about 43.6 px per paper inch. 3/32" annotation text (about 2.4 mm) is then about 4 px tall, which is illegible. At 1/4" = 1'-0", one pixel is about 1.1 real-world inches, so a 4.5" wall is about 4 px wide. Users should crop or tile sheets, export at the native resolution of the region of interest, or supply vector PDF text and DXF data rather than whole-sheet images. This is calculated from the documented 1568 px limit.

### Gaps
- No primary-source per-model Claude numbers were retrieved for FloorplanQA, ArchPlanVQA, AECV-Bench, AEC-Bench (bar chart only), or Epoch's CadEval. The arXiv PDFs were unreachable from this session (arxiv.org blocked), and the web-search budget ran out. Check before quoting.
- I found no benchmark of LLMs generating **SVG or DXF floor plans** that reports Claude-specific scores. The floor-plan generation papers found (Text-to-Layout, RLVR floor plans) do not report Claude results.
- I found no benchmark of Claude reading **IFC** or producing **Blender Python** architectural models with quantitative scores.
- Other 2026 papers seen only as titles, not read: CrossProjection (geometric grounding across views in architectural drawings, [arXiv 2608.00473](https://arxiv.org/html/2608.00473v1)), ARCH-B ([arXiv 2609.34047](https://arxiv.org/pdf/2609.34047)), RealCADBench ([arXiv 2609.03773](https://arxiv.org/pdf/2609.03773)), and "Engineering as Code" ([arXiv 2609.04216](https://arxiv.org/pdf/2609.04216)).

## 2. Known failure modes and documented mitigations

### Takeaway
The dominant failures are **silent**: geometry that compiles and reports "valid" but is wrong, invented dimensions, overlaps and clearance violations in plans, misread scale and measurement conventions, and tool bridges that report success after a failure. Claude is also unreliable at judging its own renders. The documented mitigations that work are **deterministic checks**: B-rep or geometry assertions, rule checkers, a code interpreter for metric questions, and asking the user for missing dimensions. Visual self-review alone is not enough.

### Cited Findings
- [Benchmark] Floor-plan generation errors with LLMs: "rooms with ambiguous boundaries or improper dimensions, furniture overlapping with walls or other elements, insufficient circulation space between items, and illogical door placements." The authors trace errors to "under-specified prompts or missing constraints." The paper reports **no quantitative metrics**: no overlap rate, clearance statistics, area error or connectivity rate — [Text-to-Layout, arXiv 2509.00543](https://arxiv.org/html/2509.00543v1); [Pith review](https://pith.science/paper/2509.00543)
- [Opinion] A BIM-focused newsletter argues the root cause is representation, not prompting, because general models treat layouts as images or token sequences. It lists furniture overlapping walls and doors swinging into objects as typical failures — [AI AEC Digest](https://aiaecdigest.substack.com/p/bim-transformers-layout-generation)
- [Benchmark] FloorplanQA: models fail to respect physical constraints, handle overlap, and navigate. A code interpreter does not fix planning tasks, and on shortest path it made results worse by misjudging boundary contact as collision (via search summary) — [arXiv 2507.07644](https://arxiv.org/html/2507.07644)
- [Documented test] **Silent wrong geometry**: in a six-agent test, 9 of 16 failures went unreported. A CadQuery union dropped a part's core (7,065 mm³ vs. 10,323 mm³ expected) while the solid still reported `valid=True` — [torno issue #42 research note](https://github.com/luisg0nc/torno/issues/42)
- [Anecdote] **Invented dimensions**: a sensor case was modeled at 48.5 × 12.5 mm when the real part is 55.2 × 21.3 mm — [torno issue #42](https://github.com/luisg0nc/torno/issues/42)
- [Anecdote] Hacker News on CADAM (Sept 2025, older models): hallucinated OpenSCAD functions, six iterations for a threaded part, and geometry that did not close — [HN thread](https://hn.svelte.dev/item/45140921) (relayed via [torno #42](https://github.com/luisg0nc/torno/issues/42))
- [Documented test] Xometry/Wevolver tested seven text-to-CAD tools (June 2026): **gears and manifolds mostly failed** — [Wevolver](https://www.wevolver.com/article/we-tested-7-text-to-cad-tools-are-they-actually-useful-for-engineers)
- [Vendor/Docs] Zoo: if you omit key dimensions, Text-to-CAD fills the gaps with "industry-standard assumptions." Generation can fail even when the prompt is understood, and identical prompts can give different results — [Zoo Text-to-CAD docs](https://docs.zoo.dev/docs/zoo-design-studio/text-to-cad); [Zoo "Introducing Text-to-CAD"](https://docs.zoo.dev/research/introducing-text-to-cad)
- [Anecdote] **Bridges reporting false success**: a FreeCAD MCP reported success after a failure, and an FEM force was off by 1000× (a units error) — [torno #42](https://github.com/luisg0nc/torno/issues/42)
- [Anecdote/vendor test] **Measurement-convention mismatch**: in a Revit MCP test, Claude's room areas were off because Revit measures to wall centerlines. The same test reports that Claude decoded a real RVT file correctly (Revit version, project name, all four levels with elevations, all 21 room names). The reviewer notes that MCP servers "draw and query CAD geometry; none of them renders" (via search summary) — [meltflexai Revit](https://www.meltflexai.com/blog/connect-claude-to-revit); [meltflexai AutoCAD MCP](https://www.meltflexai.com/blog/autocad-mcp)
- [Benchmark] **Weak visual self-verification**: in CADCodeVerify, the model answered questions about its own render correctly only 65–68% of the time — [torno #42](https://github.com/luisg0nc/torno/issues/42); original paper [arXiv 2410.05340](https://arxiv.org/html/2410.05340v1) [Older]
- [Benchmark] **Deterministic checks beat vision judging**: CADTests' B-rep checks agreed with human judgment 0.938 of the time vs. 0.474 for a vision-model metric. Feeding the checks back as feedback raised the pass rate from 0.715 to 0.810 — [CADTests, arXiv 2605.07807](https://arxiv.org/html/2605.07807) (figures via [torno #42](https://github.com/luisg0nc/torno/issues/42))
- [Benchmark] **Clarifying questions**: ProCAD, a proactive agent that asks for missing sizes before modeling, cut mean Chamfer distance by 79.9%. The paper notes that most text-to-CadQuery systems are one-shot — [Clarify Before You Draw, arXiv 2602.03045](https://arxiv.org/pdf/2602.03045); figure via [torno #42](https://github.com/luisg0nc/torno/issues/42)
- [Benchmark] **Correction rounds have diminishing returns**: Query2CAD gained +23.1 points over a 53.6% first try, mostly in the first correction round. CADCodeVerify stopped at two rounds, and more reasoning effort did not help monotonically — [torno #42](https://github.com/luisg0nc/torno/issues/42)
- [Benchmark] **Code-domain knowledge gaps**: AECBench found deficits in interpreting building-code tables and in complex calculation. This is the closest documented evidence on code-compliance reliability — [AECBench project page](https://archiai-lab.github.io/AECBench.github.io/)
- [Benchmark] **Drawing-set navigation**: AEC-Bench general agents failed on exhaustive traversal (checking every sheet or callout) and on cross-document coordination. They tended to rely on text extraction and keyword search over documents "whose meaning is fundamentally visual and spatial" — [Nomic blog](https://www.nomic.ai/blog/what-does-aec-bench-mean-for-aec-firms); [arXiv 2603.29199](https://arxiv.org/html/2603.29199)
- [Anecdote] **Overwritten generations**: Zoo's web app and CADAM replaced the previous model with each new generation — [torno #42](https://github.com/luisg0nc/torno/issues/42)
- [Security] Blender MCP's unauthenticated local socket executed arbitrary Python (issue #404) — [torno #42](https://github.com/luisg0nc/torno/issues/42); [blender-mcp repo](https://github.com/ahujasid/blender-mcp)
- [Validation tooling] Open-source rule checkers for LLM floor plans exist. RajNair06/floors checks overlap, door positioning and entrance requirements. A SchemaTex PR adds checks for room overlap, non-adjacent doors and out-of-room elements. A 2026 paper uses RL with verifiable rewards to cut overlapping or invalid layouts — [RajNair06/floors](https://github.com/RajNair06/floors); [SchemaTex PR #41](https://github.com/SchemaTex/SchemaTex/pull/41); [arXiv 2605.14117](https://arxiv.org/html/2605.14117v1)
- [Anecdote] KiCad forum users found **rule checkers with violation lists** the most useful AI aid (an analogous EDA domain) — [KiCad forum](https://forum.kicad.info/t/i-built-an-mcp-server-that-lets-ai-assistants-help-with-kicad-pcb-design/66451)

### Inferences
- In practice, "hallucinated code compliance" would mean Claude asserting that a plan meets egress, stair or clearance rules without computing it. The closest evidence is AECBench's code-table deficits plus the FloorplanQA constraint failures. Guides should require that every compliance claim come from a computed check (a script or rule table) that cites the clause, never from a prose assertion.
- The pattern of mitigations is consistent: put a deterministic oracle in the loop (CAD kernel validity plus volume and bounding-box assertions, shapely overlap and clearance checks, a code interpreter for distances). Use images only as a secondary sanity check, because the model's judgment of its own render is only about 2/3 reliable.
- Declare units and measurement conventions explicitly: centerline vs. finish face vs. structural face, and mm vs. inches. At least two documented failures (Revit area, FEM 1000×) are convention or unit errors, not reasoning errors.

### Gaps
- No quantitative study isolates Claude-specific rates of wall-thickness errors, opening errors, or misreading scale bars or graphic scales. These failure modes are inferred from general floor-plan generation papers and anecdotes.
- No source measured how often Claude invents code-compliance claims in architectural plans.

## 3. Workflow patterns that work

### Takeaway
The best-supported workflow is agentic and code-first. Write a spec with named parameters, units and tolerances. Ask for missing dimensions. Generate parametric code. Execute it in a real kernel. Check it with numeric assertions (bounding box, volume, clearances, overlaps). Use one rendered view as a secondary check. Allow 1–2 correction rounds, and keep the last passing version. Structured data (JSON, code, IFC) should be the source of truth, not images.

### Cited Findings
- [Benchmark] Agent harness matters: the top Parametric CAD Bench v3 entries are Claude Opus 5.5 running inside **Claude Code** or mini-swe-agent, which are agents that execute code and inspect results, not single-shot chat — [arXiv 2611.02659](https://arxiv.org/html/2611.02659v1)
- [Tool/Anecdote] **Render-and-look loop with OpenSCAD**: openscad-agent is "a Claude Code-powered 3D modeling agent environment" with automatic PNG rendering so the agent can see and self-correct, and a `preview-scad` skill renders any .scad file to PNG — [iancanderson/openscad-agent](https://github.com/iancanderson/openscad-agent); [preview-scad skill](https://www.aibuilder.sh/skills/iancanderson/preview-scad). Other examples: [andreahaku/openscad_claude_skill](https://github.com/andreahaku/openscad_claude_skill)
- [Anecdote] An XDA test had Claude Code write a .scad file, render it to PNG with the OpenSCAD CLI, then look at the image. The author's conclusion: "if you force the write, render, look, fix cycle, you get something that's at least verified somewhat" (via search summary; the article could not be fetched) — [XDA Developers](https://www.xda-developers.com/asked-claude-gpt-design-3d-prints-failed-opposite-ways/)
- [Tool] A **build123d** visual loop: the "CAD Agent" skill sends build123d commands, receives VTK-rendered images, and exports STL or STEP — [mcpmarket CAD Agent](https://mcpmarket.com/tools/skills/cad-agent)
- [Anecdote] **Cost of the visual loop**: one builder found screenshots roughly quadrupled cost. A 1280 px image is about 1,600 tokens, and Claude Code drops the oldest images in long sessions. Recommended practice: "numbers first, then one picture" — [torno #42](https://github.com/luisg0nc/torno/issues/42)
- [Benchmark/Tool] **Geometry assertions**: write dimensions as checks with an expected value and a tolerance, and re-measure them on every build. CADTests' B-rep checks agreed with humans 0.938 of the time and raised pass rates from 0.715 to 0.810 when fed back. CadQueryEval's own pass criteria (watertight, single component, bounding box within 1 mm, volume within 2%) are a ready-made assertion template — [torno #42](https://github.com/luisg0nc/torno/issues/42); [cadqueryeval](https://github.com/danwahl/cadqueryeval)
- [Tool/Benchmark] **Exact geometric queries instead of image judgment**: use feature-recognition tools (e.g., `find_holes`) and per-face B-rep data (type, area, normal, adjacency), as in AgentsCAD (arXiv 2607.02448). build123d-mcp self-reports a CADGenBench score of 0.457 with the server vs. 0.360 without, and validity rising from 88% to 100% (unverified) — [torno #42](https://github.com/luisg0nc/torno/issues/42); [pzfreo/build123d-mcp](https://github.com/pzfreo/build123d-mcp)
- [Tool] **Spec-before-geometry with stage gates**: agentcad mandates "Inspect, Specify, Build, Validate, Deliver," checks against a recorded `spec.json`, and returns to the earliest wrong stage on failure — [jdilla1277/agentcad](https://github.com/jdilla1277/agentcad)
- [Tool] **Keep the last good version**: in Amagine3D, a candidate becomes a new version only if it passes checks; otherwise the previous version is kept — [torno #42](https://github.com/luisg0nc/torno/issues/42)
- [Tool] **Parametric outputs**: Adam/CADAM turns auto-extracted parameters into sliders that change the model without another AI call. Other examples are Forgent3D's `params.json` and Zoo's feature tree — [Adam-CAD/CADAM](https://github.com/Adam-CAD/CADAM); [torno #42](https://github.com/luisg0nc/torno/issues/42)
- [Tool] **Structured feedback instead of screenshots**: the earthtojake/text-to-cad viewer (about 22k GitHub stars) added selection, annotation and measurement in Oct 2026. Its "Quick Edit" hands Claude structured annotation data rather than PNGs — [torno #42](https://github.com/luisg0nc/torno/issues/42) (citing the earthtojake/text-to-cad repo)
- [Pattern] **Claude Code hooks to enforce the loop**: practitioners use UserPromptSubmit, PostToolUse and Stop hooks to keep the build–check cycle running — [torno #42](https://github.com/luisg0nc/torno/issues/42)
- [Benchmark] **Clarify first**: asking for missing dimensions before modeling cut Chamfer distance by 79.9% (ProCAD) — [arXiv 2602.03045](https://arxiv.org/pdf/2602.03045)
- [Benchmark] **Structured layout as source of truth**: JSON-only was FloorplanQA's strongest condition. A code interpreter fixes metric questions (placement 64.5% → 95.0%) but not path or packing planning — [FloorplanQA GitHub](https://github.com/OldDeLorean/FloorplanQA); [arXiv 2507.07644](https://arxiv.org/html/2507.07644)
- [Benchmark] **Structured drawing data for document sets**: in AEC-Bench, giving agents structured drawing representations (extracted text, layout elements, reference graph) improved retrieval-heavy tasks dramatically across model families — [Nomic announcement](https://www.nomic.ai/news/aec-bench-a-multimodal-benchmark-for-agentic-systems-in-architecture-engineering-and-construction)
- [Practitioner tips] **Incremental scene building** with Blender: start with simple requests and build up, describe the end result rather than each step, break complex scenes into smaller prompts, and let each prompt build on the current scene state. Treat Claude as an agent operating a 3D tool, not a one-shot model generator — [blendermcp.org Claude guide](https://blendermcp.org/setup/claude/index.md); [UX Planet: 3D modeling with Claude Code](https://uxplanet.org/3d-modeling-with-claude-code-a-practical-blender-workflow-97e6e0b536b0); [Medium practical guide](https://medium.com/@francesco.cozzolino/a-practical-guide-to-getting-blender-mcp-working-in-blender-without-knowing-blender-473b17d6a0ef)
- [Anecdote] MindStudio's review found the Blender MCP integration "impressive but limited," best for basic object creation and scene assembly — [MindStudio](https://www.mindstudio.ai/blog/claude-blender-mcp-real-world-performance)
- [Vendor] The SketchUp connector reportedly builds geometry in a cloud SketchUp session while "verifying dimensions iteratively" — [Engineering.com](https://www.engineering.com/now-sketchup-has-an-mcp-server-for-claude-based-3d-modeling/); [Trimble release](https://news.trimble.com/2026-04-28-Trimble-Links-SketchUp-with-Anthropics-Claude,-Bringing-New-Conversational-AI-powered-Capabilities-to-3D-Modeling)

### Inferences
- A recommended architecture loop, synthesized from the above:
  1. Program/adjacency table and constraint list, as JSON with units.
  2. Clarifying questions for missing dimensions.
  3. A parametric model in code, with named parameters at the top (CadQuery, build123d, OpenSCAD, Blender Python, or ifcopenshell for IFC).
  4. Execution in a real kernel.
  5. An assertion suite (room areas vs. program, wall thicknesses, door clear widths, corridor widths, overlaps via shapely, bounding box and volume).
  6. One or two rendered views (plan and axonometric), cropped and at sufficient resolution.
  7. At most 1–2 fix rounds, then human review. Keep the last passing version under git.
- For plans, make **the JSON/IFC model the source of truth and render SVG/DXF from it**, rather than asking Claude to hand-author SVG paths. This plays to the text and structure strengths (FloorplanQA, BenchCAD, LLM4CAD) and makes checks possible.
- Make small, incremental edits ("move the door in wall W3 300 mm east") with re-validation. Create-and-edit was the weakest Parametric CAD Bench v3 workflow (best score 44.37%), so edits need extra verification.

### Gaps
- No controlled study quantifies how much the screenshot render loop improves Claude's final geometry versus numeric-assertion feedback alone. Evidence for the render loop is mostly READMEs and anecdotes, while evidence for numeric checks is benchmark-backed (CADTests).
- No published IFC-as-source-of-truth workflow with Claude was found with measured outcomes.

## 4. Prompting guidance (Anthropic + CAD-specific)

### Takeaway
Anthropic's general guidance applies directly: separate spec, context and constraints with XML tags; give 3–5 examples; state what to do (positive instructions); use extended thinking for multi-step geometric reasoning; check the model-specific prompting page. CAD vendors and practitioners add four rules: give every critical dimension and unit (or let Claude ask for them), keep each request to one part or one change, describe the end state, and expect to retry.

### Cited Findings
- [Docs] XML tags: wrap each type of content (instructions, context, input) in its own tag to reduce misinterpretation. Tag names should make sense for their contents, be consistent, and nest for hierarchy. Anthropic does not prescribe canonical tag names — [Use XML tags](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/use-xml-tags); [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Docs] Examples: use 3–5 examples for best results, wrapped in `<examples>` tags so Claude can tell them apart from instructions — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Docs] Tell Claude what to do rather than what to avoid; for example, "Your response should be composed of smoothly flowing prose paragraphs" instead of "Do not use markdown" — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Docs] Extended thinking is generally preferable to manual chain-of-thought when available. Manual CoT with `<thinking>`/`<answer>` tags still helps when extended thinking is unavailable or when you need reasoning you can review — [Extended thinking tips](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/extended-thinking-tips)
- [Docs] The current prompting reference is organized by model, with separate guides for Claude Fable 5, Opus 4.8 and others. Anthropic advises reading your model's guide first — [Prompting best practices](https://platform.claude.com/docs/build-with-claude/prompt-engineering/claude-prompting-best-practices); [claude.com best practices article](https://claude.com/resources/articles/best-practices-for-prompt-engineering)
- [Docs] Vision: verify image interpretations in high-stakes uses, and don't rely on Claude for perfect-precision image tasks without human oversight — [Anthropic vision docs](https://docs.anthropic.com/en/docs/vision)
- [Docs] Coordinates: if you scale images by hand using only the 1568 px edge limit, coordinate mappings come out wrong. Use the reference resize helper. This matters when asking Claude to locate elements on a drawing image or to click in a CAD GUI — [Vision coordinates](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)
- [Vendor docs] Zoo Text-to-CAD: include concrete dimensions. "A flange with a 50mm diameter, 6 holes, and 10mm thickness" is their example, and their "Prompt like a Pro" turns a bare "manhole cover" into "a manhole cover with cuts for lifting, 600mm diameter, 50mm thick, with a 200mm hole in the middle." Simple mechanical parts (fasteners, bearings, connectors) work best. Retry failures. Edit the resulting KCL code afterward — [Zoo Text-to-CAD docs](https://docs.zoo.dev/docs/zoo-design-studio/text-to-cad); [Introducing Text-to-CAD](https://docs.zoo.dev/research/introducing-text-to-cad)
- [Practitioner] Blender MCP: start simple and build up; describe the end result rather than the steps; split complex scenes into smaller prompts — [blendermcp.org](https://blendermcp.org/setup/claude/index.md)
- [Benchmark] Under-specified prompts and missing constraints cause most LLM floor-plan errors, so explicit constraints matter — [Text-to-Layout, arXiv 2509.00543](https://arxiv.org/html/2509.00543v1)
- [Benchmark] Text2CAD-Bench builds prompts in two styles, **geometric** (describe the shape) and **sequence** (describe the CAD operations in order). CadQueryEval task prompts describe a part "often as a sequence of CAD operations" plus its bounding box and number of connected components. Giving target bounding boxes and component counts doubles as a spec and a test oracle — [arXiv 2605.18430](https://arxiv.org/html/2605.18430v1); [cadqueryeval](https://github.com/danwahl/cadqueryeval)
- [Benchmark] Asking for clarifications before generating improves geometry (ProCAD, −79.9% Chamfer distance) — [arXiv 2602.03045](https://arxiv.org/pdf/2602.03045)

### Inferences
- A CAD/architecture prompt template consistent with this guidance:
  - `<role>` (e.g., residential architect detailing to the local code edition).
  - `<units_and_conventions>` (mm or ft-in; dimension to finish face vs. centerline; origin and axes; wall layering).
  - `<program>` as a table of rooms with target areas and adjacencies.
  - `<constraints>` (clearances, door swings, setbacks, cited code clauses).
  - `<deliverable>` (file type, parameter block at the top, named parameters).
  - `<acceptance_tests>` (bounding box, areas ±%, overlaps = 0, min corridor width).
  - An instruction to ask about missing dimensions before modeling, and to report test results rather than asserting compliance.
- Positive phrasing applies here too: "keep every wall 140 mm thick, defined as `WALL_T`" works better than "don't vary wall thickness."
- Use extended thinking (or higher effort) for layout planning and code-check reasoning. This rests on Anthropic's general guidance; I found no CAD-specific test of thinking budgets. CADCodeVerify noted that more reasoning effort was not monotonically better (relayed via torno #42), so the value of more thinking for CAD is uncertain.

### Gaps
- I could not re-verify Anthropic's long-context guidance (put long documents first and the query last) or its "give Claude a role" guidance in this session. Those page URLs exist ([long-context tips](https://platform.claude.com/docs/build-with-claude/prompt-engineering/long-context-tips), [system prompts](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-engineering/system-prompts)), but their content was not fetched.
- Text2CAD-Bench's result on whether geometric or sequence prompt style works better was not visible in the summaries.
- No Anthropic documentation specific to CAD or spatial tasks was found beyond the vision limitations and coordinate notes.

## 5. Integration surfaces and file formats

### Takeaway
There are four practical surfaces:
1. **Claude Code running headless CAD kernels** (OpenSCAD CLI, CadQuery/build123d, Blender in the background) with render and assertion loops. This is the best-benchmarked route.
2. **Official MCP connectors** launched April 28, 2026: Blender, Autodesk Fusion, Trimble SketchUp, plus community and preview Revit/AutoCAD servers.

### Inferences
- **Format guidance (inferred, not directly benchmarked).**
  - Prefer formats Claude can read and write as text and that a script can validate: CadQuery/build123d/OpenSCAD/Blender Python source, JSON program and layout files, SVG for 2D presentation, DXF (ASCII, generated via ezdxf rather than hand-written), IFC-SPF via ifcopenshell, and OBJ or glTF JSON for meshes.
  - Binary formats (.skp, .rvt, .dwg, .f3d, .blend) should go through the vendor MCP connector or a conversion library, not be pasted in.
- **Choosing a surface.**
  - Chat or Desktop with a connector (SketchUp, Fusion, Blender) suits conversational massing and early design.
  - Claude Code suits anything that needs repeatable, testable geometry (scripts, assertions, git history).
  - Computer use is a last resort for GUI-only apps, given no CAD-specific evidence and the documented spatial and coordinate limitations.
- **Artifacts.** In this research session, the Claude Code Artifact tool's own contract allows scripts from cdnjs/jsdelivr/unpkg with pinned versions. That makes three.js or SVG plan viewers feasible as published pages. This comes from the session's tool description, not a public web source; verify against current claude.ai Artifacts documentation.
